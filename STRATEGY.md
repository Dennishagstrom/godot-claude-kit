# Strategy: building a Godot game with Claude Code agents

TL;DR: keep what loads every turn small, make code easy to find, keep files small,
test headless and in parallel, one task per branch and worktree, review before merge,
and let the server decide in multiplayer. Numbers below are measured on a real Godot
4 co-op game that was built almost entirely by Claude Code agents.

## 1. Context is money

1. **CLAUDE.md loads on every turn of every agent.** Ours grew to 16.6 KB (~4k tokens).
   We cut it to 4.4 KB (-73%) by keeping only rules and pointers, and moving details to
   `docs/dev_reference.md` and milestones to `docs/status.md`. Target: < 5 KB.
2. **Big docs start with a TL;DR and a section list.** Agents read 10 lines and jump to
   one section instead of reading 20 KB.
3. **Short agent reports** (max ~40 lines). The main session pays for every line it reads.
4. **Briefs with concrete pointers** (`file:line`, known root cause, out of scope). A good
   brief saves the agent its whole search phase.
5. **No broad audits by default.** A whole-project bug sweep cost ~250k tokens. Do it
   before a big playtest, not every round. Review only what changed.
6. **End long sessions with a handoff + `/clear`.** A long session re-reads its whole
   history every turn. A fresh session from a written handoff is much cheaper.
7. **Don't resume a big agent after a long pause.** Its cache is cold; resuming a
   300k-token agent costs a lot. Start a new one with a short brief.

## 2. Find code fast

1. **`docs/code_map.md`** is generated by `tools/dev/code_map.py`: every script, its
   class, size and one-line purpose (from the `##` doc comment). Agents grep it instead
   of searching the tree. ⚠ marks scripts over 800 lines.
2. **Every script starts with a one-line `##` doc comment.** That line is the code map.
3. The pre-commit hook fails if a script was added/moved/removed without updating the map.

## 3. Small files

1. **No script over 800 lines.** An agent must read a file before it edits it; a
   2000-line script costs ~20–30k tokens every time anyone touches it, and two tasks
   can't work in it at once.
2. We split 4778 / 2563 / 2312 / 1992 / 1925-line scripts into a hub + helpers, each
   < 800 lines. Patterns that worked:
   - helpers are `RefCounted` with a back-reference to the owner, created in `_init`;
   - all `@rpc` functions and synced properties stay on the owner node;
   - the public API stays on the owner as one-line forwarders, so callers don't change;
   - big autoloads become a hub + modules (`Game.run.start()`); module scripts have no
     `class_name`.
3. **What breaks in a split:** string-named calls (`call(&"x")`, `has_method("x")`,
   `Callable(obj, "x")`, `rpc("x")`, `connect("x", ...)`) and RPC stubs. They don't show up
   as references. Reviewers must grep for them. RPC declarations must match on every
   peer (same functions, same order).
   Scripted rewrites (`_x` → `_owner._x`) can also hit text inside string literals: a
   node-name check `ends_with("_lid")` became `"_c._lid"` and chest lids silently stopped
   opening. Grep the diff for the back-reference prefix inside quotes, and run the full
   regression after a round of splits.
4. **Splits are mechanical: use Sonnet.** Measured: one big split cost ~135–190k tokens on
   Sonnet vs ~280–390k on Opus, with the same result.

## 4. Tests

1. **Everything headless.** Tests are `SceneTree` scripts (`-s res://tests/...`) that print
   `RESULT PASS/FAIL` and exit 0/1. No windows, so agents can test while you use the PC.
2. **Parallel runner** (`tools/test_runner.py`): suites in `tests/integration/suites.txt`
   with tags; timing-sensitive suites (`exclusive`) run alone at the end; a parse check
   runs first. Ours: ~150 suites in ~13 minutes at 8 jobs.
3. **One port block and one user-data folder per runner.** First we locked ports
   globally, so three agents' runners in three worktrees queued behind each other on
   the same port numbers. Now each runner claims a block (lock file), its suites get
   `<GAME>_PORT_OFFSET=block*1000` (Network, `PortOffset` and the lag proxy add it to
   every port) and a private `HOME` (own `user://`, saves, settings). Runners never wait
   for each other, and no test can touch the player's own saves. Suites of *one* runner
   still share that `user://`: give every suite its own file names or `--save=<slot>`
   (two parallel suites writing the same settings file was a flaky test the kit's own
   verification run caught).
4. **`--changed`** runs only suites whose files the diff touched (`CHANGE_TAGS` maps
   paths to tags). Agents run only their own suites (1–3 min). **One** full regression
   per round, after merging, by the main session. Three agents each running everything
   collide on ports and CPU and triple the wait.
5. **New behaviour = new test.** For multiplayer: a host + client test (two headless
   processes, `tests/net/` shows how).
6. **Wait on state, and count physics ticks, never wall clock.** A flaky test is a bug; fix
   it at once, or everyone learns to ignore red. Our flaky suites (`loop`, `enemy_nav`,
   `aim`, a safe-room gate) were fixed mainly by replacing real-time deadlines, which
   expire under load before the game gets there, with physics-tick counts. Deadlines are `seconds * physics_ticks_per_second`
   ticks. Single-process suites that simulate game time run with `--fixed-fps 60`
   (one frame = one physics tick, as fast as the CPU allows); two-process network
   suites run in real time and must tolerate several ticks per frame.
7. **Timing budgets only when alone.** Frame-time limits are asserted in `exclusive`
   suites; everything else runs with `<GAME>_PARALLEL=1` and only prints them.
8. **Split long suites** into parts listed side by side (`-- --shard=1/3`, `--roles=tank`);
   the slowest suite decides how long a parallel run takes.
9. **Pre-commit hook:** a ~2 s parse check stops broken scripts before they reach a branch.

## 5. Workflow

1. **One task = one branch (`task/<name>`) + one worktree** (`.claude/worktrees/<name>`).
   `tools/dev/new_worktree.sh` copies the `.godot` import cache (copy-on-write on macOS),
   so the worktree runs at once. `.claude/.gdignore` stops Godot from scanning the copies.
2. **Split work by files, not themes.** Big shared scripts ("hot files") have one owner
   at a time; other tasks hook in with signals and new files.
3. **Merge with `--no-ff`**, one merge commit per task: easy to find and revert.
   Commit messages `[#<task>] <what>`.
4. **Quality gate:** targeted suites green, new test exists, reviewer says `MERGE`, docs
   updated.
5. **Ask before visible windows.** You may be at work on the same machine. Until you say
   yes, everything runs headless.

## 6. Agents and models

1. **implementer** builds one task in its worktree and commits; **reviewer** reads the
   diff with the user's original task text (not the implementer's story) and gives
   `MERGE` / `MERGE AFTER FIXES` / `REWORK`.
2. **The round skill** turns a task list into merged commits: plan by file ownership,
   waves, max 3 agents at once, review, merge, full regression, handoff.
3. **Model per task:** Sonnet for mechanical work (splits, known-cause bugs, data, tests,
   docs) and for reviewers; Opus for new systems, netcode and unknown bugs.
4. **Batch small fixes** in one agent. Every agent pays to load the project.

## 7. Multiplayer

1. **Multiplayer from day one.** Retrofitting it is a rewrite. Single player = a host
   with no clients.
2. **The server decides.** Peer 1 is host and server. It simulates physics, AI, damage
   and game state. Clients send input/requests and show what they get.
3. **Validate every `any_peer` RPC on the server:** sender id
   (`multiplayer.get_remote_sender_id()`), ownership, distance, cooldown, ranges.
4. **Continuous state via `MultiplayerSynchronizer`, events via `@rpc`.** No reliable
   RPCs every frame.
5. **Late joiners get full state** (send the whole thing on join, not only deltas).
6. **`MultiplayerSpawner`**: only the server instantiates. Player nodes are named after
   the peer id; the client owns only its input node.
7. **Physics on the server only**; on clients `freeze = true` and the transform is synced.
8. Visuals are interpolated (physics at 60 Hz, drawing at screen rate), so it looks
   smooth on both host and clients.

## 8. Godot gotchas

1. **No `class_name` on autoloads.** `-s` test scripts compile class_name scripts before
   the autoloads exist, and the test fails to parse.
2. In `-s` test scripts, touch autoloads from the first `_process` frame, not in
   `_initialize()`.
3. `--headless --quit` hangs if the project has no main scene; the kit's parse check
   compiles every script with a small `-s` script instead (and catches scripts no
   scene uses yet).
4. After a merge, run `--import` before tests: new `class_name`s are unknown to the
   import cache until a scan (the runner and `finish_worktree.sh` do this).
5. Hand-edited `.tscn` files: keep `load_steps` and resource ids consistent, or build
   scenes in code.
6. Player text through `tr()` from the start; translations are then free later.
7. Logic never depends on mesh/visual node names, so visuals can be swapped.
8. The same compile-order trap hits any `class_name` script an `-s` test uses: if it reads
   an autoload member by name (`Network.players`, `Events.x.connect`) the test fails to
   compile and Godot hangs. Constants (`Network.MAX_PLAYERS`) are fine. Reach autoloads
   by path (`get_node("/root/Network")`) in reusable scripts (lint `autoload-by-name`).
9. **Exit leaks.** Godot frees scripts at exit in one order-sensitive loop. A `static var`
   holding an instance of its own class, or effect scenes instanced from code, made it
   leak "most of the game's scripts and resources", invisible until a network suite
   failed on it. The kit's `main` suite quits the real game cleanly and fails on leak lines.
10. **Randomness.** A bare `randf()` made a suite fail 1 run in 3; a replay seed came much
    later. Seeded streams per system (`Rng`) from day one cost nothing.
11. **Refactors lose RPCs.** A split dropped an RPC stub (late joiners errored, a countdown
    never synced); a scripted rename rewrote a string and no chest opened again. The kit
    diffs RPCs before every merge (`rpc_check.py`) and renames go identifier by identifier.
12. **Late join is per system.** Four separate `_on_peer_connected` handlers each missed
    something (gold, a door, a countdown). One contract (`Network.register_state`,
    snapshot + apply, queued until ready) and one test template fix the whole class.
13. **Teleports are events.** A jump sent as plain position was smoothed as motion:
    clients sat 4.5 m off for 30 s, footsteps heard a 40 m/s run. A synced serial in the
    same packet (`teleport()`) lets every listener reset.
14. **Hot-path loads.** Data resources that held PackedScenes plus `load()` per lookup cost
    66 ms a call, 3 FPS. Store paths, cache by path, build heavy scenes one per frame.
15. **Fixed fps hides per-frame bugs** (an empty navmesh, silent footsteps above 60 fps):
    keep one real-time and one high-refresh suite next to the deterministic ones.
16. **Physics layers** need names and a matrix: one hurtbox on the loot layer made arrows
    stick to pickups and desynced. The starter ships `Layers` and a test over every scene.

## 10. Optional modules

Each module is self-contained (`templates/modules/<name>/`: files, a short README that
becomes `docs/modules/<name>.md`, suite + `CHANGE_TAGS` lines). `godot-start` turns on
the recommended ones; `godot-analyse` recommends missing ones for existing projects.

- **starter** (recommended, new projects only): main menu → world → player on input
  actions (server-authoritative and spawned per roster entry in multiplayer), window and
  input settings, audio buses. Why: an empty project gives agents nothing to test against;
  the smoke test, the perf budget and the release smoke test all run the main scene, so
  they only mean something once there is one. The files are the project's from then on.
- **ci** (recommended): a GitHub Actions workflow runs every suite on push. Agents and
  friends forget to run the full regression; CI doesn't.
- **net-testing** (recommended, multiplayer): two headless processes, input via
  `Input.action_press`, asserts on what the *other* peer sees, plus `tools/lag_proxy.py`
  (rtt/jitter/loss, seedable). Why: missing RPC validation, delta-only late-join sync
  and RPC-order bugs only show with two processes; prediction and timing bugs only with
  latency. Our default lag run is 120 ms ±30 ms, 1 % loss (a typical VPN between friends).
- **build-release** (recommended): one command bumps the build number, stamps patch
  notes, exports, zips and boots the export headless (host + join for multiplayer). Patch
  notes are one file per task, so parallel branches never conflict; players see "What's
  new" once per build. Joining compares version + build: friends on different zips get a
  message instead of desyncs.
- **smooth-motion** (recommended): physics at 60 Hz, screens at 120–240 Hz. Without
  interpolation a visual stands still on ~75 % of drawn frames at 240 Hz; the test
  requires ≤ 10 % and a gap of at most one physics tick. Clients ease toward synced
  transforms. The camera follows the smoothed visual, never the body.
- **window-guard** (recommended): a plugin hook blocks commands that would open Godot or
  Blender windows until the user allows it (`/godot-claude-kit:windows on`). The user
  often works on the same machine; one focus-stealing window during a meeting costs more
  than any test. Headless, `--import`, `--export-*` and `--check-only` are never blocked.
- **perf-tests** (recommended): a budget as a test (average physics/process ms, p99 frame,
  hitches), `exclusive`. Ours caught a lookup that reloaded every room scene per call:
  physics frames of 40–350 ms against a 10 ms budget, found in the round that added it.
- **safe-saves** (recommended): `--save=<slot>`, a throwaway slot for headless runs,
  atomic JSON with backup, and a Settings skeleton that never writes the player's file in
  tests (a player's own "hitstop off" must never change a combat test's verdict).
- **l10n-check** (recommended): finds UI text built with `%`/`+` without `tr()` and
  scenes with auto-translate off. A one-second suite; translation later stays free.
- **model-import** (recommended, 3D): one check for every model, whatever made it
  (scripts, Blender by hand or over MCP, packs, generators): triangles, units, pivot, root
  transforms, materials, texture sizes, the same texture embedded in many files, Godot's
  name suffixes. Ours had one 1024² atlas embedded in 101 props and Godot extracted a copy
  per model; a model pack in the same game still does it 203 times. And a part named `lift_wheel` became a
  `VehicleWheel3D` on import. Materials named like `assets/materials/<name>.tres` become that
  shared material on import, so models batch. `docs/art_style.md` keeps the look written down:
  it is what kept 65 scripted models in one style.
- **blender-pipeline** (optional, 3D): models as short Python scripts built by headless
  Blender. What made ours look made rather than assembled: silhouette first (lathe and
  extruded outlines), bevels and trim (planks with a seeded wobble, bands, rivets), colour
  shaded light-top/dark-bottom with one palette and one material, one glow accent. Moving
  parts get their origin at the joint and hang under their parent, so a visual script
  animates them without a rig (our bosses walk, slam and open their chests that way).
  `--preview` renders a contact sheet (front, side, top, three-quarter, a player-size
  figure), because Claude judges a model only as well as it can see it. Live Blender over
  MCP is documented as an option for inspecting and fixing .blend files; what should last
  becomes a script. Organic shapes (characters, creatures) rarely work from primitives:
  make them by hand, take them from a pack or a generator, and let model-import check them.
- **data-pipeline** (optional): CSV tables → typed `.tres`, the Resource class is the
  schema. Our 144 items live in one CSV: one readable diff instead of 144 files.
- **sandbox** (optional): `-- --sandbox` arena with an F1 panel (time scale, cheats,
  spawn) that other code extends through a registry, so dev tools never call private
  game code.
- **ui-tokens** (optional): one tokens file, a theme built from it, four components and a
  test that fails on hardcoded colours/sizes in UI folders. With several agents building
  screens in parallel, this is what kept the UI one design.
- **steam** (optional, multiplayer): GodotSteam lobbies and overlay invites; the
  `SteamMultiplayerPeer` goes through `Network.adopt_peer()`, ENet stays for dev and
  tests, and everything degrades gracefully without GodotSteam. The README has the
  Steamworks checklist (fee, Playtest app, 30-day wait before release).
